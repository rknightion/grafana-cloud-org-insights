The second half of the origin question: capture the value the platform brings, so the conversation moves to upside rather than cost.

## Outcome value - what observability DID

All from grafanacloud-usage, which natively carries slug, team, service_name, integration and state on the OnCall metric:
- pages raised per observed service and per team;
- MTTA and MTTR - **p50 only.** The histogram buckets top out at 3600s so histogram_quantile SATURATES: p90 and p99 both return exactly 3600, meaning "at least an hour". Express the tail as a COUNT above the top finite bucket. And le values carry a decimal point, so le="3600" matches nothing.
- ownership completeness: share of pages carrying team="No team" or service_name="No service";
- two populations, and mixing them is roughly a fifteen-fold error: the alert-group counter spans every stack with OnCall provisioned, the response histogram only the stacks that report timing. Any ratio restricts its denominator with `and on(stack_id)`.
- a missing histogram observation means no acknowledgement was RECORDED. Say exactly that; it is not evidence nobody looked.
- humans served: dashboard opens and distinct viewers per stack from Pillar J.

## Unit economics, denominators flipped

Same inputs as Pillars B and F, pointed at value instead of waste: cost per observed service, per host, per pod, per protected service; spend per page acknowledged; spend per human who opened a dashboard.

Currency rules are unchanged and absolute: a rate-card miss is None and never zero; a partially priced card discloses what is omitted and must never present a subtotal as an estate total; mixed currencies rejected; metrics pricing declares base_rate_only or dpm_aware. Without a rate card these stay ratios and say why.

## What this is not

Not a link to ARR or pipeline. That join belongs in AirBud/Salesforce. This surface exposes org id and stack slug as the join key and stops.
